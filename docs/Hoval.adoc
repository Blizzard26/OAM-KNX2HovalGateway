= Hoval Message Protocol
:toc:
:toclevels: 4

== Overview
Hoval uses a CAN extended protocol with 50kbps as transport layer.
The session layer supports single and multi-part messages (messages consisting of several individual messages).



The Hoval Message Protocol is a CAN-based communication protocol with:

* 29-bit extended CAN identifiers (addressing)
* A message layer supporting:
  - Single messages (up to 8 bytes)
  - Multi-part messages (segmented payloads)
* A data model based on:
  - Function Code
  - Function Group
  - Function Number
  - Datapoint ID

Typical communication flow:

1. A device sends a request (e.g. read or write)
2. The target responds via broadcast
3. Messages may be single-frame or multi-part

Structure of a message:

`[Address (29 bit)] + [Payload (2–8 bytes)]`

Some information is not yet 100% clear. 
These parts are marked in #yellow#.

A lot of information can be found in the Modbus protocol description from Hoval (`TTE-GW-Modbus-datapoints.xlsx`). 

NOTE: This is not complete and there are many messages that are not documented.

=== Terminology

* Function Code: Defines the operation (read, write, etc.)
* Function Group: Logical grouping of datapoints
* Function Number: Sub-function within a group
* Datapoint ID: Unique identifier of a value
* Unit ID: Device identifier

Message Types:

* Single Message: Complete in one frame
* Multi-part Message:
  - Start Message
  - Intermediate Message(s)
  - End Message

== Analysis of the message protocol

=== Address

The address consists of 29 bits (4 bytes) (Can extended protocol).

An address encodes:

* Sequence counter (multi-part only)
* Message type (single / multi-part)
* Sender Unit ID
* Target Unit ID


Example: `1F E0 42 08`

Structure (right to left):

* Bit 25 - 29: Multi-part message counter. This always starts at 0x1F (31) and counts down from there for multi-part messages.
** Messages with a 0 serve as timer messages/pings or similar.
* Bit 23-24: Message type:
** Bit 24 = 1: flag: last message in a multi-part message
** Bit 23 = 1: flag: first message in a multi-part message
* Bit 12 - 22: _Unit ID_ of the sender (device number + device type offset)
* Bit 11 - 1: _Unit ID_ of the target (device number + device type offset; see `TTE-GW-Modbus-datapoints.xlsx`) or `0x7FF` for broadcast

=== Message

A message consists of 2 to 8 bytes

There are different types of messages:

* Message type (bit 24+23) = 11: Single messages
* Message type (bit 24+23) <> 11: multi-part message.
* Special messages

==== Single message (message type 0b11)

A single message always has at least 6 bytes

* Byte 1: Always 0x01 (see start message)
* Byte 2: Function Code - see <<FunctionCodes>>
* Byte 3: 
** Bit 8: #Unknown.# Probably first bit of function group
** Bit 7-1: Function Group (see TTE-GW-Modbus-datapoints.xlsx)
* Byte 4: Function Number (see TTE-GW-Modbus-datapoints.xlsx) (8 bits)
* Byte 5 + 6: Datapoint ID (see TTE-GW-Modbus-datapoints.xlsx) (16 bit)
* Optional: Byte 7-8: Value (8-16 bits)

==== Multi-part Message
A multi-part message consist of a start message (containing the usual header + 1 data byte) and zero or more intermediate messages (containing a multi-part message id and up to 7 data byte) and an end message.

Start → Intermediate → ... → End

The last two bytes of the data seems to be some form of a CRC (#WARNING: algorithm unknown#).

Start message:

* Contains header + first data byte
* Defines total message count

Intermediate message:

* Contains message ID + data chunk

End message:

* Last chunk + CRC

.Multi-part Message
====
```
1F5047FFx 21 0F 42 00 00 71 72 03 
1E1047FFx 0F 00 FC 01 08 02 32 00 
1D1047FFx 0F F7 04 E4 AB 00 00 00 
1C9047FFx 0F 00 DF 58
```

* Header: `21 0F 42 00 00 71 72``
* Message ID: `0F`
* Body: `03 00 FC 01 08 02 32 00 F7 04 E4 AB 00 00 00 00`
* CRC: `DF 58`
====

===== Start messages (Message Type 0b01)

A start message always has exactly 8 bytes

* Byte 1:
** Bit 8-4: Number of messages in this multi-part message (incl. start and end message).
** Bit 3 - 1: #Unknown.# Always 0b001 in my case.
* Byte 2: Multi-part Message ID - identifier for related messages in multi-part message group.
Is increased per device by one with each message 
* Byte 3: 
** Bit 8: #Unknown.# Probably first bit of function code
** Bit 7-1: Function Code - see <<FunctionCodes>>
* Byte 4: Function group (see TTE-GW-Modbus-datapoints.xlsx)
* Byte 5: Function Number (see TTE-GW-Modbus-datapoints.xlsx) (8 bits)
* Byte 6 + 7: Datapoint ID (see TTE-GW-Modbus-datapoints.xlsx) (16
bit)
* Byte 8: Value (8 bits + continuation in further messages)

=== Reading a value

A request with function code `0x40` is sent from the interface to the Unit ID of the device.
In addition to the Function Code, the message contains the FunctionGroup, FunctionNumber and Datapoint ID of the value to be read.

The recipient responds with a broadcast (destination address 0x7FF). 
The message has the function code `0x42` and contains FunctionGroup, FunctionNumber and Datapoint ID as identifying features plus the value.
If an error occurs (e.g. because the sensor / value to be read is not available), the receiver responds with a message with Function Code `0x56`.

.Reading
====
Read Request

* Address: `1F E0 42 08` 
* Message Content: `01 42 32 00 92 E2`

-> Function Code: 0x40, Function Group: 0x32, Function Number: 0x00, Datapoint ID: 0x92E2

Response:

* Address `1F D0 47 FF`
* Message Content: `01 42 32 00 92 E2 00 E7`

-> Function Code: 0x42, Function Group: 0x32, Function Number: 0x00, Datapoint ID: 0x92E2, Value: 0x00E7
====

=== Writing a value

The interface sends a request with function code `0x46` to the Unit ID of the device. 
In addition to the Function Code, the message contains the FunctionGroup, FunctionNumber and Datapoint ID as identifying features.
The new value is sent in the value bytes of the single or multi-part message.

The receiver responds with a broadcast (destination address 0x7FF). 
The message has the function code `0x42` and contains FunctionGroup, FunctionNumber and Datapoint ID as identifying features plus the (new) value.

.Writing
====
Write Request:

* Address: `1F E0 42 08`
* Message Content: `01 46 32 00 96 CE`

Function Code 0x46, Function Group 0x32, Function Number: 0x00, Datapoint ID: 0x96CE, New Value: 0x2D

Response:

* Address: `1F D0 47 FF`
* Message Content: `01 42 32 00 96 CE 2D`

Function Code 0x42, Function Group 0x32, Function Number: 0x00, Datapoint ID: 0x96CE, New Value: 0x2D
====

==== Sequence 0x52 -> 0x4C every 10s
Function Codes 0x52 and 0x4C follow a sequence. 
In particular, there is one sequence of 6 message for function code 0x52 from the BM to broadcast:
```
01 52 00 01 00
01 52 01 02 00 64
01 52 02 04 FF FF FF FF
01 52 03 02 13 0E
01 52 04 02 03 96
01 52 06 01 00
```

And there is a sequence of 15 messages for function code 0x4C from HV to broadcast:
```
01 4C 02 02 80 00
01 4C 0B 01 80
01 4C 05 01 80
01 4C 01 02 80 00
01 4C 0A 01 80
01 4C 04 01 80
01 4C 13 01 00
01 4C 11 01 00
01 4C 08 01 80
01 4C 0E 01 80
01 4C 07 01 80
01 4C 0D 01 80
01 4C 12 01 00
01 4C 14 01 00
01 4C 0F 01 00
```

It actually doesn't seem to be a request reply pattern, because sometimes there is not message from the other side, but the pattern keeps just going on.
There is a gap of 4 messages on the 0x4C side every 15 message on the 0x52 side.
